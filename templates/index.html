🔧 Correction des Données
Algorithme de correction des incohérences

Les données brutes peuvent contenir des incohérences entre TodayWins et TotalWins. Un algorithme corrige automatiquement ces erreurs. Parfois, Eric a dû éditer manuellement certaines entrées pour rattraper des plantages du jeu... qui plante parfois malgré ses améliorations (comme le stockage des stats dans Google Sheets). 😅

Principe de correction :
Pour chaque groupe de joueurs, les sessions sont traitées dans l'ordre chronologique (de la plus ancienne à la plus récente).

Pour chaque session et chaque joueur :
• On récupère le TotalWins actuel et le TotalWins de la session précédente
• On calcule le TodayWins attendu : TodayWins = TotalWins_actuel - TotalWins_précédent
• Si le TodayWins enregistré ≠ TodayWins attendu ET TodayWins attendu ≥ 0, on corrige TodayWins
• On met à jour le TotalWins précédent pour la prochaine session
• (Oui, on fait le travail qu'Eric aurait dû faire correctement dès le début, mais bon... 🤷)

Normalisation des joueurs :
Tous les joueurs présents dans les statistiques détaillées (today/total) sont automatiquement inclus dans todayWin et totalWin, même s'ils ont 0 victoires. Cela garantit que tous les joueurs qui ont participé à une session sont correctement comptabilisés dans le groupe et l'ID de session, même s'ils n'ont gagné aucune partie.

Format des données :
Les données utilisent le format todayWin[player] et totalWin[player] pour stocker les statistiques de chaque joueur.

Exemple :
Session 1 : TotalWins = 50, TodayWins = 10
Session 2 : TotalWins = 65, TodayWins = 12 (incorrect)
→ Correction : TodayWins = 65 - 50 = 15
→ (Eric aurait pu vérifier ça avant de sauvegarder, mais non, il fallait qu'on le fasse après coup)

Filtrage :
• Sessions passant minuit : si une session se termine après minuit, seule la session du jour suivant (00h-05h) est conservée
• Joueurs invalides : AIJIMMY, P1, P2, etc. sont ignorés
• (Parce qu'apparemment, Eric aime bien laisser des traces de debug dans les données de production...)

Modes de jeu (v4) :
Depuis avril 2026, Eric a ajouté un champ mode dans les stats v4. Avant ça, tout le monde jouait Head Hunters sans le savoir — comme si vous aviez le choix. Les anciennes sessions sans mode sont traitées comme Head Hunters.
Les cumuls (todayWin / totalWin) et les corrections sont calculés séparément par mode, pour qu'Eric ne mélange pas Head Hunters et Respawn 3 dans la même addition. (Il a fallu qu'on le précise nous-mêmes.)
Si une session v4 oublie le champ mode, on assume Head Hunters — parce que TowerStats doit marcher même quand Eric oublie un champ.

🏆 Classement par Pourcentage de Victoires

🏆 Pourcentage de Victoires
Comment ça marche ?

Victoires : On additionne toutes les victoires du joueur dans toutes ses sessions.

Parties : On compte toutes les parties jouées dans tous les groupes où le joueur a participé. Si une session a 4 joueurs qui ont gagné 10, 8, 6 et 4 parties chacun, cela fait 28 parties au total pour cette session.

Joueurs avec 0 victoires : Tous les joueurs présents dans une session sont comptabilisés, même ceux qui n'ont gagné aucune partie. Cela garantit que les statistiques reflètent fidèlement la participation de tous les joueurs.

Pourcentage : (Victoires ÷ Parties) × 100

Exemple : Si un joueur a 50 victoires sur 100 parties, son pourcentage est de 50%.

🏆 Classement ELO score

🏆 Classement ELO score
Qu'est-ce que l'ELO ?
Un système de classement qui évalue le niveau de chaque joueur. Plus le score ELO est élevé, meilleur est le joueur.
En savoir plus sur Wikipedia

Nouveau calcul ELO (par défaut)
• Tous les joueurs commencent à 1500 points
• Les joueurs sont classés selon leur score de session (today)
• Les confrontations sont évaluées entre toutes les paires de joueurs
• Les variations ELO sont calculées avec la formule standard (Wikipedia)
• Les variations d'une session sont appliquées en batch à la fin de la session
• Battre un joueur plus fort fait gagner plus de points
• Perdre contre un joueur plus faible fait perdre plus de points

Différence avec ELO legacy
ELO legacy mettait à jour les ratings séquentiellement à l'intérieur d'une session. L'ordre des paires pouvait influencer le résultat final.

Le nouveau calcul batch applique toutes les variations d'une session en une seule fois, ce qui rend le résultat plus stable, déterministe et plus juste par rapport aux performances globales de la session.

Interprétation de la session
Les joueurs sont classés selon leur nombre de victoires dans la session. Le meilleur gagne contre tous les autres, le deuxième gagne contre tous sauf le premier, etc.

Colonne ELO match
Deuxième métrique (à droite) : ELO recalculé match par match dans l’ordre global (dates de session, puis ordre du tableau matchsResults dans chaque enregistrement). Pour chaque match, les joueurs sont classés par nombre de kills ; les paires et le batch (somme des deltas) suivent la même règle que l’ELO session. Si une session n’a pas de matchsResults, elle n’alimente pas ce calcul ; le joueur reste à 1500 jusqu’à ses matchs comptés.

Facteur K = 32
Détermine la vitesse de changement. Plus K est élevé, plus les scores changent rapidement après chaque session (ELO session) ou après chaque match (ELO match).

🏆 Classement par Groupe

🏆 Classement par Groupe
Comment ça marche ?

Pour chaque joueur du groupe sélectionné, on additionne ses scores de chaque session (victoires du jour) de ce groupe.

Les joueurs sont classés du plus haut total au plus bas. Lorsque des filtres (ex. dates) sont appliqués, le classement est recalculé sur les sessions visibles.

Exemple : Si un joueur a eu 50, 75 et 60 victoires dans trois sessions du groupe, son score groupe est 50+75+60 = 185.

🔗 Relations de Kills

Moyenne de kills par partie

🔗 Relations de Kills
Matrice de Kills : Ce tableau montre qui tue qui. Les lignes représentent les tueurs, les colonnes les victimes.

Moyenne par partie : Les valeurs affichées représentent la moyenne de kills par partie entre deux joueurs. Cette moyenne est calculée en divisant le nombre total de kills d'un joueur sur un autre par le nombre total de parties où ils ont joué ensemble.

Exemple : Si le joueur A a tué le joueur B 25 fois au total sur 10 parties où ils ont joué ensemble, la moyenne affichée sera de 2.50 (25 ÷ 10 = 2.5). Cela signifie qu'en moyenne, A tue B 2.5 fois par partie.

Lecture visuelle : Vert = peu de kills, rouge = beaucoup de kills. Cela permet d'identifier rapidement quels joueurs sont les prédateurs de qui.

Avantage de la moyenne : Utiliser une moyenne plutôt qu'un total permet de comparer les performances entre joueurs indépendamment du nombre de parties jouées ensemble. Un joueur qui tue souvent un autre sur peu de parties aura une moyenne élevée, tandis qu'un joueur qui tue rarement mais sur beaucoup de parties aura une moyenne faible.
